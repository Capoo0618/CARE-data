## Context

`main_pipeline.py` 是 CARE-data 目前唯一的知識庫寫入端（`job()` → 爬蟲模組 → `chunk_text` → `get_embedding` → `upload_to_mongodb`），其中 `upload_to_mongodb` 的寫入與去重邏輯存在兩個已在正式環境觀察到的缺陷：

1. **部分寫入**（`main_pipeline.py:87-88`）：文章逐塊呼叫 `get_embedding()` 並個別 `insert_one`，任一塊向量化失敗只印警告並跳過該塊，其餘塊照常寫入。線上 `pid=16703` 這篇文章 `total_chunks` 宣告為 4，資料庫中實際 `chunk_index` 卻只有 `[1, 3, 4]`——第 2 塊失敗但沒有中止寫入，也沒有留下任何「未完成」的標記。此文章之後會被 `find_one` 判定為「已存在」而永久跳過，破洞不會被補上。
2. **來源級 early stopping**（`main_pipeline.py:63-67`）：爬蟲取回的文章逐篇比對，一旦遇到單篇已存在於資料庫（`collection.find_one`），就把整個 `source_name` 加入記憶體中的 `skipped_sources` 集合，直接放棄該來源後續所有文章。若來源列表不是嚴格依時間新到舊排序，或中間某篇曾因寫入失敗（缺陷 1）而未真正入庫，後續原本應該新增的文章永遠不會被檢查到。實測佐證：衛福部闢謠網站（HPA，`hpa.gov.tw/wf/newsapi.ashx`）API 回傳 1,000 筆文章，資料庫中卻只有 910 個對應 URL。

此外，`scraper_api.py:32`、`scraper_tfc.py:37,86` 三處呼叫來源網站時都帶有 `verify=False`（略過 TLS 憑證驗證），以及 repo 內存在一份過時的 `test_pipeline.py`——它是 `main_pipeline.py` 加入 early-stopping 之前的舊副本，自帶一份不同步的 `chunk_text`／`get_embedding`／`upload_to_mongodb`，檔名雖以 `test_` 開頭但不含任何 assertion、`unittest` 不會收集它，只會持續佔用 repo 空間並可能誤導後續讀者。

## Goals / Non-Goals

**Goals:**

- 寫入知識庫的每篇文章要嘛所有 chunk 都成功寫入，要嘛完全不寫（全有或全無），不留部分寫入的破洞
- 去重判定的粒度從「來源」降到「文章」，避免單篇已存在就使同來源後續新文章被永久略過
- 讓有提供修改日期的來源（衛福部闢謠網站／HPA）能在文章改版時觸發重新寫入
- 移除爬蟲對來源網站請求中的 `verify=False`，恢復 TLS 憑證驗證
- 刪除過時的 `test_pipeline.py` 副本

**Non-Goals:**

- 不改變 `chunk_text` 的切塊邏輯或 `get_embedding` 的輸入格式——`chunk_content` 內容與既有向量完全不受影響，本 change 不涉及下游 CARE Backend 的重建或 cutover（清洗與切分品質留給另一個 change `etl-content-quality` 處理）
- 不對食藥署來源做「修改日期」推斷，也不新增其來源本身不具備的欄位
- 不引入內容雜湊比對作為更新判定依據（見 D3）
- 除 `certifi`（D4 需要）以外不新增相依套件

## Decisions

### D1. 為何是「全有或全無」而非「補寫缺塊」

補寫缺塊需要先知道哪些 `chunk_index` 缺了，但現行 schema 的 `total_chunks` 只是寫入當下宣告的值，不保證與資料庫中實際筆數一致——`pid=16703`（`total_chunks=4`，實際只有 `chunk_index=[1,3,4]`）就是反例，代表無法單靠現有欄位可靠地重建「應該有哪些塊」。而且部分寫入的文章在語意上本來就不完整：缺的那塊可能正好包含使用者提問所需的答案，讓 RAG 檢索到不完整內容比完全查無此文更危險。每篇文章只有數個 chunk，整篇重新處理的成本很低，比起「先偵測缺塊、再只補缺的部分」的額外複雜度，全有或全無在正確性上更明確、實作與驗證都更簡單。

### D2. 為何用集合差集而非移除去重

去重機制本身仍然必要——若移除，每天排程都會把整批來源重新切塊、重新呼叫 embedding API，成本隨資料量線性增加且平白重算未變更的內容。問題不在「要不要去重」，而在「去重判定的粒度」：現行邏輯以「來源」為單位，一篇已存在就放棄整個來源；改為以「文章」為單位後，去重邏輯改成一次以 `collection.distinct()` 取回既有的 url／title 鍵值集合，再對每篇來源文章做集合成員比對，取代逐篇呼叫 `find_one()` 的 N 次資料庫往返。以目前庫中約 1,600 篇文章的規模，一次性取回鍵值集合的記憶體成本可忽略。

### D3. 更新判定只用「修改日期」

三個來源（食藥署、衛福部闢謠網站、台灣事實查核中心）中，目前只有衛福部闢謠網站（HPA）的 API 回應含有可用的修改日期欄位；食藥署 API 與台灣事實查核中心網頁都沒有對應欄位，這兩者的文章維持現行「已存在即跳過」，視為不可偵測更新。刻意不採用內容雜湊比對作為替代方案：雜湊比對雖然能涵蓋所有來源，但會讓 `utils.py` 任何一次清洗邏輯的微調（例如調整去除的 HTML 標籤或空白正規化規則）都連帶讓雜湊值改變，觸發知識庫的全量重寫與重新嵌入，付出的重建成本遠高於此變更本身要解決的問題。

### D4. 為何是釘選中繼憑證，而不是直接移除 `verify=False`

移除 `verify=False` 後衛福部（`hpa.gov.tw`）立即連不上：該伺服器的 TLS 交握只送出
自己的伺服器憑證，沒有附上簽發它的中繼憑證 `TWCA Secure SSL Certification Authority`。
瀏覽器與 macOS 的 curl 會依憑證中的 AIA（Authority Information Access）欄位自動去下載
缺少的中繼憑證，所以人工測試時看起來一切正常；但 Python 的 `ssl` 模組**不做 AIA 補抓**，
於是憑證鏈斷在中繼這一層，驗證失敗。

三個選項的取捨：

- **繼續用 `verify=False`**：等於對所有來源關閉 TLS 驗證，任何中間人都能竄改寫進
  醫療知識庫的內容。這正是本 change 要解決的問題，排除
- **只對衛福部保留 `verify=False`**：範圍小一點，但被竄改的仍是佔知識庫 65% 的來源，
  而且會留下一個沒人記得為什麼存在的例外，排除
- **釘選中繼憑證（採用）**：把該中繼憑證存進 `certs/`，執行時與 certifi 的根憑證庫
  合併成一份完整的 CA bundle。驗證仍然完整進行，只是補上了伺服器沒送的那一段

中繼憑證是公開資料（任何連線都會傳送），存進 repo 不涉及任何機密。
它的鏈仍然終止於 certifi 收錄的 `TWCA Global Root CA`，不是自簽信任。

**到期行為**：釘選的憑證有效期至 2030-10-16。到期後衛福部會連不上，
該來源本次一篇都抓不到，於是 D5 的來源檢查會讓 CI 紅燈——**失敗是響亮的，不是無聲的**。
另一個失效情境是未來的 certifi 移除了 `TWCA Global Root CA`：單靠釘選的中繼憑證救不回來
（Python 預設不設 `X509_V_FLAG_PARTIAL_CHAIN`，憑證鏈必須終止於自簽根憑證），
但同樣會被 D5 抓到。

### D5. 為何是「資料面 fail-open、訊號面 fail-loud」

兩支爬蟲模組都以 `except Exception as e: print(...)` 處理失敗，函式仍會正常回傳
（只是少了那個來源的資料）；`job()` 的 MongoDB 區塊同樣如此。實際後果：
**衛福部（佔知識庫 65%）可以完全停止更新，而測試 11/11 全綠、GitHub Actions 綠燈、
退出碼 0**——這不是假設，是 D4 實作過程中真的發生的（既有的 `test_02` 只斷言食藥署的標題，
衛福部掛掉它不會失敗）。

沒有改成「任一來源失敗就整個中止」：那會讓一個來源的暫時問題阻擋其他兩個來源的正常更新，
把一個部分故障放大成完全故障。採用的規則是：

- **資料面 fail-open**：能抓多少就寫多少；單一來源失敗、單篇文章寫入失敗，都只跳過該項
- **訊號面 fail-loud**：只要有來源全滅或有文章寫入失敗，該次執行以非零狀態碼結束

`find_missing_sources` 刻意只看「有沒有產出」而不看數量：來源本身的文章數會自然波動，
設數量門檻會產生假警報；而「一篇都沒有」幾乎必然是故障。

常駐排程模式（本機開發）刻意**不**因單次失敗終止程序，只有 `GITHUB_ACTIONS=true`
的單次執行模式才 `sys.exit(job())`。

### D6. 既有資料為何只補日期，而不是全量重算

線上 4,339 筆切片**全部沒有 `updated_at` 欄位**（本次變更才開始寫入）。
若把「舊文件沒有日期」直接當成「日期不同」，改版偵測會判定**每一篇**既有的衛福部文章
都改版了，合併後首次執行就要刪除並重新向量化 910 篇、2,840 個切片。
`get_embedding` 每個切片有 2 秒節流，光是 sleep 就 95 分鐘以上，加上 Gemini 配額限制，
實際會跑數小時、極可能被 GitHub Actions 的 6 小時上限砍掉，並連續數日紅燈——
而換來的只是「內容多半相同」的重算。

採用的做法：舊文件沒有日期時只 `update_many` 補上 `published_at` / `updated_at`，
不重新向量化。補完之後，之後每一次真正的改版都能正常偵測。

**代價**：若某篇在本次變更之前就已於來源改版，那一次改版會被漏掉。
這是一次性且有界的，遠低於全量重算的成本。

### D7. 既有破洞的一次性修復

D6 讓既有文章不再被重寫，但這個 change 的第一個動機正是「部分寫入留下的永久破洞」
（`pid=16703` 宣告 4 塊、實際只有 `chunk_index [1, 3, 4]`，之後被判定「已存在」而永遠跳過）。
Task 2 的全有或全無寫入只能保證**新的**破洞不再產生，補不了既有的。

因此在 D6 的補日期分支裡加一道判斷：**實際切片數與文件宣告的 `total_chunks` 不符時，
改走重寫路徑**。線上實測有 71 篇這樣的文章、遺失約 141 個切片，全部集中在衛福部；
修復成本約 277 個切片、預估 10 分鐘，相較 D6 避免掉的數小時完全可負擔。

只在「沒有 `updated_at`」的分支檢查即可：補完日期之後由改版偵測接手，
而新的破洞在全有或全無寫入之下已不可能產生。
