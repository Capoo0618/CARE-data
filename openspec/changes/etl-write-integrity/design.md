## Context

`main_pipeline.py` 是 CARE-data 目前唯一的知識庫寫入端（`job()` → 爬蟲模組 → `chunk_text` → `get_embedding` → `upload_to_mongodb`），其中 `upload_to_mongodb` 的寫入與去重邏輯存在兩個已在正式環境觀察到的缺陷：

1. **部分寫入**（`main_pipeline.py:87-88`）：文章逐塊呼叫 `get_embedding()` 並個別 `insert_one`，任一塊向量化失敗只印警告並跳過該塊，其餘塊照常寫入。線上 `pid=16703` 這篇文章 `total_chunks` 宣告為 4，資料庫中實際 `chunk_index` 卻只有 `[1, 3, 4]`——第 2 塊失敗但沒有中止寫入，也沒有留下任何「未完成」的標記。此文章之後會被 `find_one` 判定為「已存在」而永久跳過，破洞不會被補上。
2. **來源級 early stopping**（`main_pipeline.py:63-67`）：爬蟲取回的文章逐篇比對，一旦遇到單篇已存在於資料庫（`collection.find_one`），就把整個 `source_name` 加入記憶體中的 `skipped_sources` 集合，直接放棄該來源後續所有文章。若來源列表不是嚴格依時間新到舊排序，或中間某篇曾因寫入失敗（缺陷 1）而未真正入庫，後續原本應該新增的文章永遠不會被檢查到。實測佐證：衛福部闢謠網站（HPA，`hpa.gov.tw/wf/newsapi.ashx`）API 回傳 1,000 筆文章，資料庫中卻只有 910 個對應 URL。

此外，`scraper_api.py:32`、`scraper_tfc.py:37,86` 三處呼叫來源網站時都帶有 `verify=False`（略過 TLS 憑證驗證），以及 repo 內存在一份過時的 `test_pipeline.py`——它是 `main_pipeline.py` 加入 early-stopping 之前的舊副本，自帶一份不同步的 `chunk_text`／`get_embedding`／`upload_to_mongodb`，檔名雖以 `test_` 開頭但不含任何 assertion、`unittest` 不會收集它，只會持續佔用 repo 空間並可能誤導後續讀者。

## Goals / Non-Goals

**Goals:**

- 寫入知識庫的每篇文章要嘛所有 chunk 都成功寫入，要嘛完全不寫（全有或全無），不留部分寫入的破洞
- 去重判定的粒度從「來源」降到「文章」，避免單篇已存在就使同來源後續新文章被永久略過
- 讓有提供修改日期的來源（衛福部闢謠網站／HPA）能在文章改版時觸發重新寫入
- 移除爬蟲對來源網站請求中的 `verify=False`，恢復 TLS 憑證驗證
- 刪除過時的 `test_pipeline.py` 副本

**Non-Goals:**

- 不改變 `chunk_text` 的切塊邏輯或 `get_embedding` 的輸入格式——`chunk_content` 內容與既有向量完全不受影響，本 change 不涉及下游 CARE Backend 的重建或 cutover（清洗與切分品質留給另一個 change `etl-content-quality` 處理）
- 不對食藥署來源做「修改日期」推斷，也不新增其來源本身不具備的欄位
- 不引入內容雜湊比對作為更新判定依據（見 D3）
- 不新增相依套件

## Decisions

### D1. 為何是「全有或全無」而非「補寫缺塊」

補寫缺塊需要先知道哪些 `chunk_index` 缺了，但現行 schema 的 `total_chunks` 只是寫入當下宣告的值，不保證與資料庫中實際筆數一致——`pid=16703`（`total_chunks=4`，實際只有 `chunk_index=[1,3,4]`）就是反例，代表無法單靠現有欄位可靠地重建「應該有哪些塊」。而且部分寫入的文章在語意上本來就不完整：缺的那塊可能正好包含使用者提問所需的答案，讓 RAG 檢索到不完整內容比完全查無此文更危險。每篇文章只有數個 chunk，整篇重新處理的成本很低，比起「先偵測缺塊、再只補缺的部分」的額外複雜度，全有或全無在正確性上更明確、實作與驗證都更簡單。

### D2. 為何用集合差集而非移除去重

去重機制本身仍然必要——若移除，每天排程都會把整批來源重新切塊、重新呼叫 embedding API，成本隨資料量線性增加且平白重算未變更的內容。問題不在「要不要去重」，而在「去重判定的粒度」：現行邏輯以「來源」為單位，一篇已存在就放棄整個來源；改為以「文章」為單位後，去重邏輯改成一次以 `collection.distinct()` 取回既有的 url／title 鍵值集合，再對每篇來源文章做集合成員比對，取代逐篇呼叫 `find_one()` 的 N 次資料庫往返。以目前庫中約 1,600 篇文章的規模，一次性取回鍵值集合的記憶體成本可忽略。

### D3. 更新判定只用「修改日期」

三個來源（食藥署、衛福部闢謠網站、台灣事實查核中心）中，目前只有衛福部闢謠網站（HPA）的 API 回應含有可用的修改日期欄位；食藥署 API 與台灣事實查核中心網頁都沒有對應欄位，這兩者的文章維持現行「已存在即跳過」，視為不可偵測更新。刻意不採用內容雜湊比對作為替代方案：雜湊比對雖然能涵蓋所有來源，但會讓 `utils.py` 任何一次清洗邏輯的微調（例如調整去除的 HTML 標籤或空白正規化規則）都連帶讓雜湊值改變，觸發知識庫的全量重寫與重新嵌入，付出的重建成本遠高於此變更本身要解決的問題。
